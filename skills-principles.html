03 / Skills & principles

技术栈是工具
原则决定边界

从 AI 应用、数据检索到前端交付，技术选择都围绕项目里的具体问题展开。这一页整理实际采用的方法，以及做取舍时使用的判断标准。

使用方式技术选型先服从问题的复杂度，再考虑流行度。一个清楚的规则、约束或数据库事务，通常比多引入一层智能更可靠。
03.1 / Built in projects

项目中的方法

AI 应用

Python、FastAPI、LangChain、LangGraph、MCP 和手写 ReAct。主要用于检索增强生成、工具调用、多 Agent 编排和流式响应。

我更关注工具边界、状态管理和失败路径，而不是只把模型调用包在一个函数里。

数据与检索

PostgreSQL、pgvector、Milvus、BM25、RRF、Rerank、Redis 和 jieba。实际工作包括数据隔离、索引迁移、检索融合、缓存和计数。

检索系统需要同时关注召回质量、证据可解释性、延迟和数据更新成本。

前端与交付

HTML、CSS、JavaScript、Vue 3、UniApp、TypeScript、React 和 Next.js。这些技术分别用于个人站、家庭菜单和项目中的交互页面。

部署侧使用 Docker Compose、Nginx、Linux、HTTPS 和阿里云服务器，能够把页面、接口和数据服务放到同一条可检查的链路上。

工程质量

SQLAlchemy 2 异步 ORM、Alembic、JWT 鉴权、pytest、SSE、幂等设计和数据库事务。工程质量不只靠测试数量，还要确认测试真的执行到了关键边界。

用评测集和回归测试复查一次改动的收益，也记录依赖、延迟和可维护性方面的代价。

03.2 / Working principles

四条工作原则

先问是否真的需要 Agent

能用一次模型调用、明确规则或固定流程解决的问题，不增加自主循环。Agent 会引入不确定性、成本和运维负担，它应该解决真实的协调问题。

没有停止条件的循环就是事故

每个自主循环都要有步骤上限、Token 预算、墙钟上限和人工接管点。写不出停止条件，就不应该上线。

约束必须可以被验证

“回答要有出处”不能只写在提示词里，还需要引用结构、代码级校验和评测集。说不清怎么检查的约束，等于没有约束。

不为了新技术而上线

如果一层新技术只带来很小的收益，却增加延迟、依赖或故障面，就应该主动关掉。把取舍写进默认配置，比在分享里讲一句更可靠。

可靠性不是一句态度，而是把边界、证据和回滚路径写进系统。
