MCP 首次调用 59.6 秒：三个瓶颈叠在一起

2026-10-26 · 项目三 · DevFleet

第一次调用 MCP 工具，从发出请求到拿到结果用了 59.6 秒；同样的调用第二次只要 6.0 秒。这 53 秒的差不是网络抖动，是三件事各付了一次性成本，而它们叠在了同一个请求上。

一、进程启动：约 18 秒

MCP 服务端用 stdio 传输，意味着每次拉起都要新起一个 Python 进程、导入全部依赖、初始化客户端。冷启动时这些开销全算在第一个请求头上。用python -X importtime 看了一遍，光是向量库和 HTTP 客户端的导入就占了十秒出头。

二、握手与工具发现：约 4 秒

initialize 协商能力，紧接着 tools/list 把工具清单和 JSON Schema 全部返回。工具不多，但 schema 描述写得细，一坨结构体来回两趟，四秒就没了。这部分每次连接都要重来一遍。

三、首次检索：约 30 秒

这一项最容易被忽略。向量集合没有预热，第一次查询要触发索引加载，冷加载比后续查询慢一个数量级。日志里那条 31 秒的 span，几乎全是等 Milvus 把段加载进内存。

四、把一次性成本挪到别处

  • 守护进程常驻：服务端不再随请求启停，启动成本从每次变成每次部署。
  • 工具清单缓存：tools/list 的结果按版本缓存，连接时只做能力协商。
  • 启动即预热：进程起来后立刻发一条轻量查询把集合加载进来，别等第一个真实用户。

三项做完，首次调用从 59.6 秒降到 6.0 秒，和第二次的耗时基本一致——说明冷启动的额外开销已经被摊平了。

冷启动的耗时永远落在第一个用户身上。如果你的产品是「打开就能用」，那这个成本必须提前付掉，不能留给线上。

这类优化没有算法含量，全靠把时间线拆开看：哪一段是每次都要付的、哪一段只付一次、哪一段可以提前付。拆清楚之后，能挪的挪走，剩下的才是真成本。
