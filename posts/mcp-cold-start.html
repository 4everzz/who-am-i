MCP 首次调用 59.6 秒：三个瓶颈叠在一起

2026-10-26 · 项目三 · 小家开饭啦

第一次调用 MCP 工具，从发出请求到拿到结果用了 59.6 秒。把启动、握手和清理链路拆开后，修复后的同一条验收链路降到 6.0 秒。这是单条冷启动验收数据，不代表平均响应时间。

一、真正卡住的是启动与握手

MCP 服务端用 stdio 传输，冷启动时需要拉起子进程、导入依赖并完成 session.initialize() 握手。最初我只给 call_tool 加了超时，结果真正卡住的握手仍然没有被限制，用户还是要等将近一分钟。

二、清理阶段会把超时抵消

给握手加上超时后，另一个问题才暴露出来：异常清理时调用 aclose() 还会等待卡住的子进程，前面的超时又被抵消。建立连接和清理连接必须分别设上限，清理失败也不能拖住用户请求。

三、把一次性成本从请求里移走

最终方案是把“启动 + 握手”整体纳入超时范围，清理单独设置更短的超时，并用模块级单例和异步锁复用已经建立的会话。这样外部 MCP 依赖即使启动慢，也不会让主流程无限等待。

四、把一次性成本挪到别处

  • 分段设超时：建立连接、工具调用和清理阶段各自有明确上限。
  • 复用会话：模块级单例配合异步锁，避免并发请求重复冷启动。
  • 失败可降级：外部服务不可用时返回可解释结果，不让主流程一直转圈。

三项做完，首次调用从 59.6 秒降到 6.0 秒，和第二次的耗时基本一致——说明冷启动的额外开销已经被摊平了。

冷启动的耗时永远落在第一个用户身上。如果你的产品是「打开就能用」，那这个成本必须提前付掉，不能留给线上。

这类优化没有算法含量，全靠把时间线拆开看：哪一段是每次都要付的、哪一段只付一次、哪一段可以提前付。拆清楚之后，能挪的挪走，剩下的才是真成本。
