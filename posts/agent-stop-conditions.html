Agent 循环没有停止条件，就是在等事故

2026-10-27 · 项目一 · DevFleet

Agent 出事故，很少是因为「模型太笨」，多数是因为它在一个错误的方向上很努力，而系统没有机制让它停下来。

一、一次真实的跑飞

工具返回空结果，模型认为「再试一次可能就有了」，于是用几乎相同的参数又调了一遍。因为每次调用的参数略有不同，去重逻辑没拦住。四十分钟后 token 预算烧完，任务状态还是「进行中」。

事后看，代码里只有一句 while True，退出条件写在模型自己的判断里。模型的判断是不可靠的——它没有「我已经试过五次」这种跨轮记忆，除非你显式告诉它。

二、四道闸，缺一不可

  • 步数上限：max_steps 到点强制收口，哪怕没得出结论，也要输出「当前进展 + 卡在哪」。
  • token 预算：按累计消耗算，不是按单次。超了就降级成单轮回答。
  • 墙钟上限：用户等待有耐心上限，30 秒没结果就该给中间态，而不是让他盯着转圈。
  • 人工接管点：涉及写操作、对外发送、删除的动作，必须停在确认这一步。

三、重复调用要能被识别

光有步数上限不够。第 3 步和第 7 步调同一个工具、传同一份参数，本质上是在原地打转。做法是给每次工具调用算一个签名（工具名 + 参数哈希），同一个签名出现两次就降级：告诉模型「这个调用刚才已经试过，返回为空，换一条路」。

有界自主不是限制能力，是让失败可预期。跑飞十分钟和跑飞四十秒，区别不在模型，在闸门。

现在这条链路的默认值：max_steps=10、单任务 token 预算、30 秒软超时给中间态、写操作双确认。参数看着保守，但它保证最坏情况下用户拿到的是一个明确的「没做成 + 原因」，而不是页面一直转。
