DevFleet 把这些收进一个每句话都能给出处的研发资料库：这个任务该谁做、这个改动该不该合、这次构建为什么失败，一次问清楚。

How I Work

四条工作原则

项目之外的一些判断标准，也决定了代码最后长什么样。

  1. 01

    先问「真的需要 Agent 吗」

    能一次模型调用或固定流程解决的，不加自主循环。上 Agent 意味着引入不确定性、成本和运维负担，它是负债，不是资产。

  2. 02

    没有停止条件的循环就是事故

    每个自主循环都要有步数上限、Token 预算、墙钟上限和人工接管点。写不出停止条件，就不该上线。

  3. 03

    约束必须能被验证

    「回答要有出处」不是一句口号，得有代码级校验和评测集去查。说不出怎么检查的约束，等于没有约束。

  4. 04

    不为了用新技术而上线

    给检索加了一层重排，39 题对照实验里首位命中率只提升不到 0.1 个百分点，每次却要多等 405 毫秒——于是主动关掉，并把这个决定写进默认配置。

01 / 个人项目 · 0 → 1

DevFleet

Multi-Agent 研发协作平台

问题

研发判断一条 PR 能不能合并，要在任务、代码改动、评审意见、构建日志与本地文档之间来回跳， 一个 PR 常要看五六个页面。信息是散的，结论也就没法复核。

目标是把这些信息组织成一个可检索、可引用的证据库，让 AI 回答三个具体问题： 这个任务该谁做、这个改动该不该合、这次构建为什么失败。

做法

研发数据底座

经 GitHub REST API 同步六类数据（任务、代码改动、评审意见、构建记录、失败日志、项目文档）， 单 / 多仓库周报一次汇总。统计数字由代码聚合，不让模型生成。

有出处的问答

结构感知切片后语义 + 关键词双路召回，再 Rerank 二次排序；按 repo_id 隔离， 强制编号引用、可回溯原文。Milvus 不可用时自动降级为关键词检索，宁可答得糙也不答不出。

多智能体编排

分诊、审查、排障各交给一个专职 Agent；跨领域问题由 Planner → Orchestrator → Observer → Synthesis 拆解，按依赖并行执行， Observer 专门校验证据缺口与结论冲突，输出可逐条核对的合入建议。

写操作要人点头

评论、关任务、加标签统一转为 ActionDraft，过权限校验与人工确认才真正调用 GitHub API， 全程落 AuditLog；SSE 实时推送工具调用与执行进度。

关键取舍

为什么要拆成多 Agent，一个 Agent 加工具不够吗？

单 Agent 处理跨领域问题时，检索、审查、排障的证据会挤在同一段上下文里互相污染， 而且一旦答错很难判断是哪一步出的问题。拆成三个专职 Agent 后，每段上下文边界清晰、失败可归因。

代价是链路更长、失败点更多，所以配了两条硬约束：单任务 90 秒超时，依赖失败沿链路传播并跳过下游—— 一个环节挂了不会把整条链路卡死。

周报数字为什么不让模型算？

让模型数数是最容易出错、又最难被发现的地方。新增多少任务、合并多少 PR、失败多少次构建， 这些由代码聚合后直接填进模板，模型只负责组织语言。数字和措辞的责任分开。

向量库挂了怎么办？

降级为关键词检索。回答质量会下降，但结论仍然带出处、仍然可核对， 比直接抛一个 500 更有用。降级会显式标注，不假装一切正常。

为什么写操作一定要人工确认？

评论、关闭 Issue、加标签会改变外部状态，而且不可撤销。所以统一先生成草稿， 权限校验通过后等人点确认，最后写审计日志。执行过程用 SSE 实时可见， 能看到调用了什么工具、进度到哪一步。

结果

209项自动化测试通过
6类研发数据统一接入
5 → 1合并审查的核查入口

Agent、检索与结构化输出均有评测集校验；架构、开发与部署由我独立完成。

02 / 个人项目 · 已上线

小家开饭啦

家庭饮食管理与 AI 助手

问题

家庭成员每天要在群聊里反复商量吃什么、买什么、冰箱还剩什么，信息不同步， 食材经常放到过期。目标是把这些集中到一处，并且让 AI 助手能按现有食材给建议。

做法

多端交付

一套 UniApp + Vue 3 代码交付 H5 / 微信小程序 / App，统一请求层处理令牌与跨端差异； 管理后台是独立的 Vue 3 工程。H5 与小程序已上线，App 已打包、待上架。

后端与数据完整性

FastAPI + SQLAlchemy 2 异步栈，JWT 鉴权与家庭级数据隔离； 并发加入家庭的上限竞态用 SELECT … FOR UPDATE 行锁收敛， 成员唯一约束保证邀请码加入幂等；Alembic 管理 33 条迁移，库存增减包在事务里。

手写 ReAct 与 MCP

不依赖 LangChain，手写 ReAct 循环：5 个只读工具、最多 4 步强制收口， 写入一律由用户确认后走业务接口。经 MCP 接入《中国食物成分表》，按来源标注可信度。

平台治理与成本

管理后台做内容审核、通知去重、审计留痕与三级角色逐接口校验； Redis Lua 原子计数限每人每日 50 次 AI 调用；对话历史按 6 轮 / 300 字符 / 工具 50 条裁剪； SSE 断连即取消后台任务。

关键取舍

为什么手写 ReAct，不用现成框架？

这个场景只需要 5 个只读工具、最多 4 步，引入一套 Agent 框架的抽象成本高于收益。 手写能精确控制停止条件——步数满了怎么收、工具报错怎么退、什么时候必须把决定权交回用户。

两个人同时用邀请码加入，会不会超员？

会。计数和写入如果分两步查再做，中间就有竞态窗口。 所以加入家庭时用 SELECT … FOR UPDATE 锁住家庭行再计数， 配合成员唯一约束，重复提交也不会产生第二条成员记录。

为什么只给 AI 只读工具？

模型可以建议「把这袋食材标记为用完」，但不能自己改库存。 写操作全部回到业务接口、由用户点确认，AI 只负责查和提议。 这样即使模型判断错了，也不会留下不可撤销的脏数据。

限流为什么用 Redis Lua？

「读计数 → 判断 → 写回」三步如果分开执行，并发请求会同时通过。 Lua 脚本在 Redis 里原子执行，计数与判定不会被打断，配额才是真的 50 次。

结果

50+核心用户（按实际使用人数）
59.6 → 6.0sMCP 首次调用
381 + 12后端 / 管理后台测试

已上线：menu.zmeety.cn（H5 与微信小程序）。 家庭成员常共用一个账号，用户数按实际使用人数统计。

03 / RAG 检索与问答质量工程

智愿通

高考志愿填报智能体 · 检索与问答质量工程

问题

高考志愿填报高峰期，学生与家长反复查询「这个分数能上什么学校」「这个专业有什么要求」， 招生老师每天重复回答。信息散落在各省考试院官网、高校招生网与 PDF 章程里，人工比对耗时且易错。

结构化语料含 13 省 65 万余行招生与分数位次，另有院校档案。 难点不是「能回答」，而是答案里的每个数字都能回溯出处，并且不该拒答的不拒答。

做法

检索

pgvector 向量召回 + tsvector 关键词召回双路并行，用 RRF 融合排序； jieba 的领域词典从结构化库动态读取约 2,000 个高校名与 1,200 个专业名， 数据更新后自动跟随，「郑轻」「河大」这类简称不再漏检。

可信与引用

回答强制带编号引用，并做代码级校验；自建句级断言的忠实度评测， 报告带指纹防过期、逐题落盘可断点续跑。编造内容直接判不合格。

事实保护

LangGraph 状态机串联「抽取 → 校验 → 参数化 SQL → 冲稳保打标 → 事实校验」， 模型改写过的分数、位次一律打回重来。条件缺失时引导补全，而不是猜。

评测与数据质量

100 题评测集（39 基础 + 61 口语化难题）；147 条规则的数据质量引擎扫描 213,283 行， 定位 17 条失败规则，其中 8 条会直接导致答错。测试从 0 建到 1,416 条。

关键取舍

为什么最后把 Rerank 关掉了？

39 题四档消融里，从 wide 到 rerank 首位命中率提升不到 0.1 个百分点，延迟却增加 P50 +405ms / P95 +625ms。收益很小、成本是确定的，所以保留能力、默认关闭， 并把这个结论写进配置注释，避免以后有人再「顺手加上」。

「19/35 → 0/35」到底是什么指标？

是域门控的误拒答率，不是事实错误率。也就是 35 道本该能回答的问题里， 有 19 道被错误地拒绝了，修完之后是 0 道。

把它说成「事实错误」是错的——忠实度是断言级指标，没有这个分母。

忠实度第三次为什么从 0.95 掉到 0.92？

因为主动收紧了高风险断言的门控：宁可判得更严，也不放过可能改写分数位次的回答。 用 2.7 个点的忠实度换更硬的事实约束，这个交换是有意做的，不是回退。

为什么一定要强制引用？

志愿填报答错的代价太高。没有出处的回答无法核对，也无法在出问题时定位是数据错、检索错还是生成错。 强制引用把「信不信」变成「查不查得到」。

结果

22.3 → 7.0s提问到出字（-69%）
19 → 0误拒答（35 题中）
+2.56 / +2.13首位命中率 / 排序质量（pt）
0.86 → 0.95 → 0.92忠实度（末次主动收紧）
1,416自动化测试
147数据质量规则

内部验收版本，未做公网部署。指标均为本地评测实测。
